SQL注入笔记：POST提交Referer注入

一、 漏洞原理分析

通过分析靶场源码（Less-19 index.php）可以发现：

  1. 输入过滤： 后端对用户输入的 username 和 password 使用了自定义的 check_input 函数进行安全检测和过滤，因此无法直接在账号密码字段进行普通的 SQL 注入。
  2. 头部信息获取： 当账号密码验证通过后，后端会通过 $_SERVER['HTTP_REFERER'] 获取 HTTP 请求头中的 Referer 信息，以及获取用户的 IP 地址。
  3. 插入操作： 获取到的 Referer 和 IP 信息被直接拼接到了 INSERT INTO 语句中存入数据库：
  1. 漏洞成因： 由于 $referer 变量在存入数据库前没有经过任何安全过滤，攻击者可以通过抓包篡改 HTTP 请求头中的 Referer 字段，利用闭合单引号并拼接恶意 SQL 函数，从而引发 SQL 注入。

二、 了解 Referer 头

  • 定义： Referer 是 HTTP 请求头（Header）的一部分。当浏览器向 Web 服务器发送请求时，一般会带上 Referer，告诉服务器该请求是从哪个页面链接过来的。
  • 常见用途：
    • 防盗链： 服务器可以通过判断 Referer 是否为自身域名，来决定是否允许加载图片等资源。如果不是，则进行拦截。
    • 防止恶意请求： 用于验证请求的来源是否合法。
  • 冷知识： Referer 的正确英语拼写应该是 referrer。但由于早期 HTTP 规范中的拼写错误，为了保持向下兼容，这个错误的拼写就一直沿用至今。
  • 注意： 如果用户是直接在浏览器地址栏输入网址访问的，请求头中通常是不包含 Referer 字段的。

三、 注入实战演示 (报错注入，以Less-19为例)

由于页面不会直接回显数据库的查询结果，但会将数据库执行的错误信息输出在页面上，因此这里采用报错注入的方式（如利用 extractvalue() 或 updatexml() 函数）。

操作步骤：

  1. 正常输入账号密码（如 admin / admin）点击登录。
    • 注意这里一定要输入正确的账号和密码登录成功才可以，只有登录成功，程序才会去获取你的Referer和IP头，然后再执行INSERT INTO 语句将这些头部信息存入数据库的 referers 表中。
  2. 使用代理工具（如 Burp Suite）拦截该 POST 请求。
  3. 将拦截到的请求发送到 Repeater（重发器）模块。
  4. 在请求头中找到 Referer 字段（如果没有可以手动添加），并修改其值为恶意的 Payload。
